## Player experience

- In team management, agree on the seven established Beverage amounts once and press **Finalize team Beverage Rules**. Finalized rules are read-only, reused across league/tournament games and future seasons. HR limits remain competition/game settings and keep their existing audited correction behavior.
- On the Beverage page, each account-linked player has one **Opt out** / **Participate** button for the selected team. This choice persists across devices and seasons for that team. A player cannot change another player's choice. Captain designation does not affect scoring or participation permissions.
- Opt-out stops both charges and credits on subsequently saved at-bats; existing owed balances and credits remain. All baseball statistics, HR use/limits, batting advancement and HR Bands continue normally. Rejoining resumes the same team rules on future saves. No per-game Beverage editor appears once this capability is enabled.
- Existing games/history are retained. Teams are not silently finalized or assigned replacement values at rollout. An existing live game with different Beverage values must be completed before conflicting team rules can be finalized; matching values may be finalized while it remains live. New games require finalized team rules. Existing games remain scoreable while the team completes this setup.
- Account-linked players start with the existing participating behavior until they explicitly opt out. Guests have no account to operate a personal toggle; their established behavior is retained. Membership without a linked player never permits toggling a teammate or guest.

## Executable schema and command design

The canonical executable is `../migrations/20261014022554_team_beverage_rules.sql`. It was created with `supabase migration new`, populated with the reviewed SQL, tested locally, then applied once after explicit approval. Its filename matches Supabase's returned history version. The former `team_beverage_rules.sql` proposal now points to this applied file. `node scripts/prepare-beverage-proposal.cjs` verifies the canonical SQL body against `team_beverage_base.sql` and the three existing source definitions; it neither connects to a database nor modifies an applied migration. Original draft comments were updated to identify approval; the executable SQL is unchanged from review.

New private, RLS-enabled, deny-by-default tables:

1. `team_beverage_settings`: one team key, monotonic safe-integer revision, nullable rules, finalizing actor/time. Rules contain exactly the existing seven integer amounts in [-100,100]. Once finalized, the rules and finalizing identity/time cannot change or be deleted. No automatic finalization/backfill.
2. `beverage_commands`: stable team/command ID, authenticated actor, operation, exact payload, accepted revision, response and server timestamp. History is immutable. Same actor/payload/ID retries return the original receipt without changing current state; another actor or payload with that ID is rejected. Stale expected revisions conflict and require review.
3. `beverage_participation_events`: immutable team/player/revision/choice/command rows. Composite foreign keys and lookup indexes keep teams separate and historical lookups bounded. The write RPC derives the player from `auth.uid()` and active team membership; it accepts no player ID, actor, timestamp, season, balance or retroactive switch.

Add `scoring_plays.beverage_revision` default 0 and `scoring_play_revisions.beverage_participating` default true. The first play insert captures the team's sequence while holding the settings row lock. The revision insert derives participation for that batter as of that original boundary. Existing plays remain sequence 0/participating. Later corrections to the same batter retain the original choice; correcting the batter derives that batter's choice at the original boundary, never their current preference. Game dates and client clocks cannot backdate participation. Voids remain zero.

The team settings row orders preference changes, finalization, new game starts and first play acceptance. Existing season/day/tournament locks, scoring revisions, membership checks, retry fingerprints, immutable originals, rule versions and audit receipts remain. Preference writes hold no day/season/tournament locks. Finalization reads legacy game rules without taking scoring row locks. No new circular lock order is introduced. A concurrent toggle and save is determined by which transaction obtains the team row lock first; a save cannot use an uncommitted preference.

Only three private functions are replaced, guarded by read-only verified live hashes:

- `start_scoring_game`: `6af474e10978b30d6da280ee8b76ce0a`. After existing duplicate/revision checks, lock/read the canonical team rules and reject missing finalization or differing Beverage values. HR limits and other setup checks retain their original behavior. Old duplicate command receipts still work after finalization.
- `scoring_game_evaluation`: `ca6c7206ee5258ff8f8044d64ad7ea55`. After established stats/HR evaluation, set the play's Beverage delta to zero only if its captured participation is false. Include the captured flag in the authorized play projection. Preserve effective HR corrections, Bands, negative totals and all other formulas.
- `read_scoring_season`: `a961286b4f29d932c00cd48659bd1b35`. Add own-team Beverage state and `capabilities.teamBeverage`; existing aggregates and metadata remain.

Public APIs `da_read_team_beverage(p_team)` and `da_change_team_beverage(p_team,p_command,p_expected,p_change)` are authenticated invoker wrappers over fixed-search-path private definer functions. Each private entry point explicitly verifies `auth.uid()` and current membership. All active team members may finalize the agreed rules, consistent with existing shared team setup; finalization is permanent through the app. Participation additionally requires their own non-guest account-linked roster row. Anonymous execution and direct private table access are explicitly revoked. Helper/trigger functions have no client execute grant. Existing auth/RLS/grants, Cloudflare Access, bindings and scoring access are unchanged. No service key or user metadata authorization.

## UI and failure behavior

The controls show only authoritative RPC state; they never optimistically claim Saved. Lock simultaneous clicks. Uncertain saves retain the exact command ID/payload for retry and disable new changes. Conflicts reload state and require a new deliberate click; a late duplicate opt-out cannot undo a subsequent rejoin. Offline controls are disabled. Team changes/unmount invalidate late UI responses. After a confirmed save, reload current state rather than applying an old receipt as today's choice.

Before the migration exists, unsupported RPCs expose no fake toggle. After rollout, new-game setup sends canonical team values internally, excludes the per-game editor, and directs unfinalized teams to team management. Opponent-only tournament continuation, dates, optional lineups and fixed Bands are preserved. Normal scoring gains no new menu or form.
